# 프로젝트 컨텍스트 (단일 진실 공급원)

이 문서가 코드베이스 탐색을 대체한다. **여기 없는 정보는 아래 참조 파일에서 찾고, 거기에도 없을 때만 파일을 직접 읽어라.**

**갱신 의무:** 설계 결정 변경·새 파일·새 패턴 발생 시 같은 커밋에서 이 문서 또는 해당 참조 파일을 갱신한다.
**작성 규칙:** **규칙만 적는다.** 어떻게 알아냈는지·무엇을 실측했는지·어떤 대안을 기각했는지는 적지 않는다(단, "되살리지 말 것"은 규칙이므로 남긴다). 사연의 정본은 **그 결정이 사는 소스 파일의 주석 하나**다 — CLAUDE.md·HISTORY.md·커밋 메시지에 다시 풀어 쓰지 않는다.
**상한: 이 파일 120줄.** 넘기면 새 줄을 더하지 말고 **먼저 같은 분량을 참조 파일로 내리거나 지운다.** 이 파일은 모든 작업이 통째로 읽으므로 길이가 곧 비용이다.

## 원본 기획
[docs/SPEC.md](../../../docs/SPEC.md) — 설계자 브리프 원문. **요구사항의 정본이다.**
스펙에 없는 것을 구현자가 정했으면 그 결정은 이 문서에 적는다(스펙 원문은 고치지 않는다).

## 현재 상태
**스택(Vite + React + TS + zustand) + OS 셸(바탕화면·작업 표시줄 HUD·공용 창) + `일정` 창까지 있다(2026-08-10).**
게임 시스템(업무·직원·정산·세이브)은 아직 없다(`src/systems/`에는 달력 환산뿐). 셸 상세는 `references/shell.md`.
코어 설계 정본: [docs/superpowers/specs/2026-08-10-webdi-core-design.md](../../../docs/superpowers/specs/2026-08-10-webdi-core-design.md)

## 게임 컨셉
- 웹브라우저용 **회사 운영 게임**. UI 전체가 가짜 윈도우 OS다 — 플레이어는 웹디자이너 1인 회사 대표
- 바탕화면의 프로그램(피그마·포토샵·VS코드·카톡·네이트온·아웃룩·일정·브라우저·작업물 폴더)이 곧 게임 메뉴다
- 톤: **귀엽고 트렌디**. ⚠️ windowsGame의 뉴트럴 OS 크롬과 다른 방향이다 — 코드를 베껴 오더라도 팔레트는 베끼지 않는다

## 확정된 설계 결정
스펙에서 그대로 오는 것 + 구현 중 정해진 것. **표에 없으면 아직 안 정해진 것이다.**

| 항목 | 결정 |
|---|---|
| 시간 구조 | **주 단위 턴.** 주중이 기본, 주말은 **일할지 선택**(확률적 클라이언트 돌발 이벤트가 주말을 연다) |
| 정산 | 월말마다 **"유지보수보고서"** 메일로 월정산(`isSettleWeek` = 주차 % 4, 달력과 같은 단위). 고정 지출은 `SUBSCRIPTIONS`(피그마·포토샵) — ⚠️ 직원 급여가 생기면 여기 더하지 말고 **직원 목록에서 계산**한다(사람 수가 정본). 소지금이 음수가 되는 것이 파산인데 **게임 오버 화면은 아직 없다** — 정산 메일이 알릴 뿐이다 |
| 소모 자원 | `행동력`(프로그램 실행마다 소모, 레벨업으로 증가 — 초반은 업무 1개치) · `정신력` · `소지금` |
| 회사 축 | `회사평판` · `회사레벨` |
| 회사등급 | 극소/소/중소/중견/대 5단(`COMPANY_GRADES`). **평판에서 파생하고 저장하지 않는다**(내려가기도 한다). 지는 값은 **채용 상한 하나**다 |
| 플레이어 스탯 | 6종 + `기획력`(`planning` — 미팅에서 알아내는 키워드 수만 정한다. 시작 30은 임시치): `디자인`·`퍼블리싱`·`CS`·`피그마 숙련도`·`포토샵 숙련도`·`코딩 숙련도`. ⚠️ **숙련도 3종은 업무 시간을 줄이는 축**이고 디자인/퍼블리싱/CS는 **할 수 있는 퀄리티를 정하는 축**이다 — 섞지 말 것 |
| 직원 스탯 | **디자인/퍼블리싱/CS 3종만.** 숙련도는 없고 **레벨**이 업무 시간을 줄인다 |
| 직원 종류 | 웹디자이너 / 웹퍼블리셔 / **디블리셔**(디자인+퍼블리싱) |
| 업무 종류 | 팝업제작+업로드 / PPT 제작 / 사이트제작(시안 → 퍼블리싱) |
| 업무 실행 | 프로그램 실행 = 행동력 소모. 행동력이 남는 한 **몇 개든 중첩 가능**. 퀄리티를 스탯 범위 안에서 고르고 **퀄리티가 높을수록 행동력을 더 먹는다** |
| 수주 경로 | ①업무 수주 사이트 ②클라이언트가 메일/카톡으로 직접. **업무 요청은 무작위 + 데드라인 있음** |
| 의뢰 결정 | 채널이 고를 수 있는 것을 정한다(`components/JobActions.tsx`, 광고 글은 없음): **메일 = 견적보내기 / 거절하기**, **고객게시판 = 확인 하나** — 이미 계약된 업체라 거절이 없다. 수주하면 스토어 `jobs`에 한 줄이 오르고 계기판의 업무목록 판에 뜬다 — **`job.id` = 그 글의 id**라 한 의뢰가 두 업무가 되지 않는다. 거절은 `rejectedIds`. ⚠️ **완료는 사람이 켜지 않는다** — `completeJob`(한 방향)이 취소선을 붙이고, 지금은 부르는 곳이 없다(공정의 줄이 생기면 마지막 공정이 부른다) |
| 의뢰가 오는 곳 | **신규 의뢰 = `메일`(바탕화면), 유지보수 의뢰 = `사내시스템 > 고객게시판`.** 둘은 같은 목록(`src/data/inbox.ts`)의 `channel`로만 갈린다. 안 읽은 수는 스토어 `readIds` 하나에서 파생해 아이콘 뱃지로 붙는다(`PROGRAMS.badge`가 아이콘 ↔ 채널 짝) |
| 업체 관리자 페이지 | 브라우저 **주소창에 처음 한 번은 직접 쳐야** 닿는다(첫화면 바로가기 칸에 넣지 않는다) — `사내시스템 > 업체정보`에서 주소·계정을 찾아 옮겨 적는 왕복이 의도된 동선이다. 로그인은 `CLIENTS`의 계정과 대조한다. 안에는 **팝업 목록 + 등록 폼**이 있다(목록에서 게시 기간을 고칠 수 있다 — 오타를 되돌릴 길이 없으면 한 번의 실수가 영구 클레임이 된다) |
| 팝업 고리 | **제작(포토샵) → 등록(관리자 페이지) → 판정(주차 넘김) → 클레임**. ⚠️ **비용은 제작만 진다**(고른 퀄리티의 행동력) — 등록은 값을 물리지 않는다(되돌리지 말 것: 한 팝업에 두 번 문다). 만든 파일은 **업체를 가리지 않고 전부** 등록 화면 select에 뜬다 — 걸러 주면 "틀린 파일"이라는 실수가 성립하지 않는다. 파일 id에 `jobId`를 심어(`popupFileId`) 판정이 파일 목록 없이도 출처를 안다. ⚠️ **등록은 그 업무의 업체에 올려야** 공정이 오른다(남의 관리자 페이지에 올리면 진행되지 않는다). ⚠️ **제작을 회신하지 않은 파일은 등록 폼에서 잠긴다**(감추지 않고 잠근다 — 사라지면 왜 없는지 알 수 없다). 안 잠그면 팝업은 걸리는데 공정은 안 올라 같은 팝업을 두 번 걸게 된다. ⚠️ 의뢰의 **`dueWeeks > toWeeks`**가 불변식이다 — 완료 회신이 게시 기간 종료 후라 마감이 기간 안이면 지킬 수 없는 기한이 된다(`inbox.test.ts`가 지킨다). 클레임 메일도 **그 업무의 채널로** 간다 |
| 팝업 판정 | `systems/popup.ts`의 **순수 함수** `judgePopups(week, jobs, popups) → Claim[]`. 세 갈래: `wrong-file`(남의 파일) · `overstay`(기간 지났는데 있음) · `missing`(기간인데 없음). ⚠️ **같은 업체·같은 주는 한 건**이다(메일 한 통, 평판 한 번 `CLAIM_REPUTATION_LOSS`). 기간은 **양끝 포함**. 완료(`done`) 업무는 검사하지 않는다. 스토어는 결과를 **적용만** 한다 |
| 요청 기간의 정본 | **의뢰다**(`Request.popup`의 `fromWeeks`/`toWeeks`, 상대값). 수주 시점에 `job.popup.from/to`로 **굳는다**(마감과 같은 이유). 플레이어가 등록 폼에 적는 기간은 **사본이 아니라 주장**이고, 둘이 어긋나는 것이 곧 클레임이다 |
| 주차 진행 | `advanceWeek` 하나뿐이고 계기판 주차 판의 `다음 주` 버튼이 **묻는 창을 거쳐** 부른다(`Hud.tsx`의 `Confirm` — 되돌릴 수 없는 일이라 한 번 묻는다). ⚠️ **행동력을 다 써도 그 주에 머물 수 있다** — 넘기는 것은 늘 사람의 선택이고, 자동으로 넘기지 말 것. 행동력을 `apMax`로 **완전 회복**(이월 없음)하고, 그 자리에서 팝업을 판정해 클레임 메일·평판 하락을 적용한다. ⚠️ **평판은 0 밑으로 안 내려간다** |
| 게임 중 생기는 메일 | 클레임은 스토어 `claims`에 쌓이고 `inbox('mail', claims)`로 **같은 받은편지함**에 선다(새 글이 위). ⚠️ 뱃지를 세는 곳(`Desktop`·`Mail`)은 `unreadCount`에 `claims`를 **반드시 넘긴다** — 빠뜨리면 뱃지만 조용히 어긋난다. 클레임은 `ad: true` 갈래라 견적보내기가 붙지 않는다 |
| 채용 | 브라우저 채용사이트에 **공고 업로드** → 지원자 발생 |
| 종료 조건 | **무한 샌드박스.** 게임 오버는 **둘**: **파산**(월말 정산에서 소지금 음수) · **폐업**(아래 평판 위기). 엔딩·도감 **없음 — 만들지 말 것** |
| 평판 위기 → 폐업 | 회사평판 **0~100**. 이 값 하나가 수주 사이트를 정한다(낮으면 단가 하락 → 위기선 아래면 **아무것도 안 뜸**). 평판 < `REPUTATION_CRISIS`(10)면 매주 ①신규 수주 0(메일·카톡 의뢰도 끊김) ②**직원 1명 퇴사, 레벨 높은 순** ③경고 메일. `crisisWeeks` **4 도달 시 폐업**. 평판이 위기선 위로 오르면 **0으로 리셋**. ⚠️ 위기 중에도 **기수주 업무는 진행 가능** — 그 납품과 CS 응대가 유일한 탈출구다 |
| 폐업은 파생이 아니다 | ⚠️ **폐업을 파산에 얹어 파생시키지 마라.** 직원이 다 나가면 급여도 사라져 지출이 줄기 때문에, 평판 0짜리 회사가 잔고만 두둑하면 아무것도 안 하며 수십 주를 버틴다(할 일도 죽을 길도 없는 구간). 그래서 **명시적 카운터**를 둔다 |
| 행동력 = 시간 | ⚠️ **별도의 "시간" 자원을 만들지 마라.** `공정 1회 비용 = 퀄리티 비용(하1·중2·상3) − 숙련도 감면(40+ → −1, 80+ → −2)`, **하한 1**(0이면 무한 실행으로 붕괴). 시작 3, 회사레벨 +1마다 +1, 매주 완전 회복·**이월 없음** |
| 제작 퀄리티 | 공정 실행은 **세 갈래 중 하나를 고른다**(`data/game.ts`의 `QUALITY`): 간단하게(행동력1·F~B) / 열심히(2·C~A) / 매우 신경써서(3·S~SSS). **밴드는 퀄리티가, 그 안의 칸은 스탯이 정한다**(`systems/craft.ts`의 `gradeOf` — 순수·무작위 없음). 밴드가 겹치는 것(B/C)은 의도다. 결과 등급은 만든 순간 파일에 굳는다(`files[].grade`·`drafts[].grade`) |
| 스탯 vs 숙련도 | ⚠️ **등급은 스탯**(디자인/퍼블리싱/CS)이, **비용 감면은 숙련도**(피그마/포토샵/코딩)가 정한다. 이 둘을 뒤바꾸는 것이 이 게임의 단골 사고 지점이다. ⚠️ 스펙 초안의 "스탯이 퀄리티 **상한**을 정한다(`<34 하`…)"는 **폐기했다** — 상한으로 잠그면 초반엔 고를 것이 하나뿐이라 선택 자체가 없다. 지금은 셋 다 고를 수 있고 낮은 스탯은 **낮은 등급**으로 벌한다 |
| 업무 = 공정의 줄 | 팝업[포토샵 제작→브라우저 업로드] · PPT[PPT 창 제작] · **사이트[PPT 화면정의서→피그마 시안→에디터 퍼블리싱]**(설계자 확정, 2026-08-12). 순서대로만 진행 — 앞 공정이 안 끝나면 뒷 공정 창에 그 업무가 뜨지 않는다. **업로드 공정은 퀄리티 없이 행동력 1 고정** |
| 납품 = 메일 회신 | **공정을 끝내는 것과 업무가 끝나는 것은 다르다**(설계자 확정, 2026-08-12). 프로그램에서 공정을 실행하고, 그 결과는 **그 업무를 요청한 글(메일·고객게시판)에 회신**해야 상대에게 간다 — 회신 전에는 완료가 아니고, 그 사이 마감이 지나면 계약 파기다. ⚠️ 회신은 **행동력을 먹지 않는다**(팝업 등록과 같은 이유 — 결과를 올리는 손짓이지 공정이 아니다). ⚠️ `completeJob`을 부르는 것은 **회신이다** — 공정 실행(`publishJob` 등)은 그 업무의 단계만 올린다 |
| 공정은 한 번씩 | 실행(`step`)과 회신(`replied`)을 **따로 센다**(`systems/pipeline.ts`). 같을 때만 다음 공정이 열리고, `step > replied`일 때만 회신할 수 있다. ⚠️ 그래서 **회신 전에 다시 만들 수 없다** — 퀄리티를 고르는 순간이 곧 결정이다(버튼이 비용과 나올 등급을 미리 적는 이유). 게임 중에 생긴 글은 스토어 `mails` **한 목록**이다(클레임·답장·완료 메일이 같이 산다) |
| 시안 키워드 + 미팅 | 사이트 업무에만 붙는다. **클라이언트가 원하는 키워드 5개(`SITE_KEYWORDS`)는 저장하지 않는다** — `업무 id`를 씨앗으로 하는 순수 함수가 낸다(`systems/keywords.ts`의 `clientKeywords`, `Math.random` 없음). 저장하는 것은 **미팅에서 알아낸 것뿐**(스토어 `meetings`). 수주하면 그 주에 미팅 알림이 그 업무의 채널로 오고, 피그마에서 **행동력 `MEETING_AP`(1)**를 물고 참석한다(업무당 한 번 — 두 번 열면 행동력으로 정답을 살 수 있다). ⚠️ **기획력(`planning`)이 알아내는 개수를 정하고 최고치도 5보다 적다**(`MEETING_REVEAL`) — 다 알면 미팅 뒤 선택이 사라진다. 적중 수 → `KEYWORD_SHIFT`가 **등급을 민다**(`gradeOf`의 셋째 인자). ⚠️ **대금·평판에 따로 곱하지 않는다** — 등급이 이미 `GRADE_REWARD`로 흐른다. ⚠️ 보정은 **퀄리티 밴드 밖으로** 나간다(밴드 안에서 자르면 다 맞혀도 헛일이고 다 틀려도 벌이 없다). 절반(2~3개)이 기준선 0이다 — 찍어도 평균 절반은 맞기 때문. **직원 파견은 아직 없다**(`store.holdMeeting` 옆에 자리만 주석으로 남겼다) |
| 회신이 여는 다음 공정 | 공정이 여럿인 업무는 **회신할 때마다 상대의 답장이 받은편지함에 새 글로 온다**(설계자 확정, 2026-08-12). 그 답장이 곧 다음 공정의 요청이고, **마지막 공정의 회신만 완료 회신**이다. ⚠️ 답장은 클레임과 같은 자리(스토어에 쌓여 `inbox('mail', …)`로 선다)를 쓰되 `jobId`·`step`을 지고 있어야 어느 업무의 몇 번째 칸인지가 한 방향으로 정해진다 |
| 완료 보상 | **완료 회신에서 지급된다**(`systems/money.ts`의 `reward`) — 보수 = `BASE_FEE[kind]` × 등급 배율, 평판도 같은 표(`GRADE_REWARD`)에서 온다. **C가 기준선**(배율 1.0·평판 0)이고 등급이 없으면(퍼블리싱만 있는 업무) 기준선을 쓴다. ⚠️ **평판 clamp는 스토어 한 곳**(`clampReputation`)에서만 한다. 평판은 **가장 낮은 등급**이 정한다(약한 고리 규칙). **완료 회신을 보내면 클라이언트의 만족도가 적힌 완료 메일이 온다**(설계자 확정, 2026-08-12) — 그 메일 한 통이 결과를 전하는 유일한 자리다(보수·평판 변화도 여기서 읽힌다). ⚠️ 만족도는 새 축이 아니라 **그 업무 공정들의 등급에서 파생**한다(약한 고리 그대로 — 가장 낮은 등급이 만족도를 정한다) |
| 직원 축 | 내가 직접 = 행동력 1~3 / **즉시**. 직원 지시 = 행동력 **1 고정** / **N주 뒤**(`N = 기본 주차 − 레벨 보정`, **하한 1**). 지시받은 직원은 N주간 점유. 종류가 맡을 수 있는 공정을 제한(디블리셔만 시안+퍼블리싱 둘 다) |
| 데드라인 | **모든 의뢰에 기한이 있다**(`Request.dueWeeks`, 상대값). 수주하는 순간 `job.due = 지금 주차 + dueWeeks`로 **굳는다** — 상대값으로 두면 주가 지나도 남은 기한이 안 준다. **표시는 날짜다**(`systems/calendar.ts`의 `formatDate`/`formatPeriod` — 마감·팝업 게시 기간을 쓰는 모든 화면이 같은 함수를 쓴다. 한 주 7일 고정이라 달은 28일까지다. 마감·기간 끝은 그 주의 **마지막 날**, 기간 시작만 첫날. `formatWeek`(N째 주)은 제작 시점·메일 도착처럼 **한 점**을 말할 때만 남는다). 남은 주 ≤ `DEADLINE_URGENT_WEEKS`면 업무목록에서 빨갛게 선다. 초과 = **계약 파기**(주차 넘김에서 판정 — 대금 0 · 평판 `BREACH_REPUTATION_LOSS` · 파기 메일 · `job.breached`로 표시하고 목록에서 지우지 않는다). ⚠️ **만들어 놓고 회신하지 않은 것도 깨진다** — 납품은 보내는 일이다. ⚠️ **위약금 없음** — 현금 직접 차감은 초반 즉사를 만든다. 손해는 태운 행동력과 평판을 통한 다음 달 수입 감소로 문다 |
| CS 스탯 | 클라이언트 응대(메일·고객게시판). **수주 단가와 평판 회복률**만 올린다. 업무 공정에는 관여하지 않는다 |
| 퍼블리싱(에디터) | **FTP 연결 → 업체 폴더 → 그 업체의 미완료 업무 → 줄 클릭 = 즉시 실행**(`PUBLISH_AP`를 물고 `completeJob`이 붙는다 — 사이트 업무의 마지막 공정이라 여기가 그 첫 호출자다). 연결은 `systems/ftp.ts`가 `CLIENTS[].ftp`와 대조하고(기본 경로는 안 본다) 결과만 스토어 `ftpClients`에 남는다. ⚠️ **팝업 업무는 목록에도 없고 `publishJob`이 한 번 더 막는다** — 여기서 done이 되면 주차 넘김 판정이 그 업무를 건너뛰어 클레임을 피하는 구멍이 된다. ⚠️ 업무↔업체는 `job.from` = `CLIENTS[].name`으로 잇는다 — **FTP 정보가 없는 신규 고객(문구점 등)은 에디터에 못 뜬다**(수주가 업체를 만드는 고리가 생기면 풀린다) |
| 즐겨찾기 | 브라우저 주소창의 별로 켠다. 스토어 `bookmarks`(정규화한 주소 문자열)가 정본이고 **이름은 `siteTitle`이 주소에서 뽑는다**. ⚠️ 도착한 주소에만 별이 뜬다 — 처음 찾아가는 왕복은 남기고 **반복 방문만** 짧아진다 |
| 메신저의 상대 | **직원이다** — 업무 지시와 보고가 오간다. 클라이언트는 여기 오지 않는다(메일·고객게시판이 진다). ⚠️ 대화방 = 고용된 직원 하나이므로 채용 전에는 목록이 비어 있는 것이 맞다. 스펙의 "클라이언트가 카톡으로 직접"은 별도 창이 생길 때 다시 본다 |
| 시작 수치 | 행동력 3은 코어 설계 확정. ⚠️ **정신력 100 · 소지금 100만 · 평판 30은 스펙에 없는 임시치**(`src/data/game.ts`) — 곡선이 정해지면 조정한다 |
| 달력 환산 | **한 달 = 4주 고정**, 통산 1주차 = 1년 1월 1째 주. 실제 달력 주 경계를 쓰면 월말 정산 주차가 달마다 흔들린다 |
| 사내시스템 | **바탕화면 프로그램**으로 둔다(스펙은 브라우저 접속으로 적었다 — 옮길 일이 생기면 `Company.tsx`를 사이트 컨테이너에 넣으면 된다). 메뉴: 회사현황(평판 게이지) · **업체별** 접속 정보(FTP·관리자 계정). 업체는 여러 개다 — `CLIENTS`는 수주 시스템이 생기면 스토어 목록으로 바뀐다(모양 유지) |
| 이름 있는 슬롯 | 자동저장과 **다른 자리**다(`systems/save.ts`) — 자동저장은 늘 직전 한 순간만 들고 있어 지나간 판으로 못 돌아간다. 3칸, 키 `webdi.slot.<n>`, ⚠️ **자동저장 키와 섞지 않는다**(섞으면 한쪽이 다른 쪽을 덮어 정본이 사라진다). 한 칸에 **상태 + 요약**(주차·소지금·평판·업무 수)이 같이 앉는다 — 요약이 있어야 목록에서 세이브를 안 풀고도 어느 판인지 안다. ⚠️ 저장 대상 목록의 정본은 `store.ts`의 **`saveFields` 하나**다(자동저장 `partialize`도 같은 것을 쓴다 — 두 벌로 두면 슬롯에만 안 담기는 축이 생긴다). ⚠️ 슬롯 내용을 스토어에 들이지 않는다(세이브 안에 세이브가 들어간다) — 화면은 `slotsRevision`이 바뀔 때 저장소를 다시 읽는다. ⚠️ 저장소 글자는 못 믿는다(`parseSlot`이 깨진 것을 **붓기 전에** 빈 칸으로 떨어뜨린다 — 부어 넣고 죽으면 되돌릴 자리가 없다). 불러오기·새 게임·덮어쓰기·삭제는 전부 **한 번 묻는다**(`window.confirm` 금지). 빈 슬롯에는 불러오기·삭제 버튼을 **아예 그리지 않는다**. 새 게임은 판만 되돌리고 **슬롯은 남긴다** |
| 세이브 | zustand `persist`, `localStorage` 키 **`webdi.save.v1`**. 판이 바뀌면 키를 v2로 올린다 — 옛 세이브는 그 순간 남의 키가 되어 **마이그레이션 없이 새 게임**이 된다. ⚠️ 저장 대상은 `partialize` **한 곳**에서 고른다(열린 창은 제외) — **새 상태 축을 더하면 그 목록에도 더해야 한다**(빠뜨리면 그 축만 조용히 안 남는다). 테스트(node)에는 `localStorage`가 없어 아무 데도 안 쓰는 저장소로 떨어진다 |

## 디자인 토큰
⚠️ **CSS는 정의되지 않은 var를 만나면 그 선언 전체를 무효로 만든다** — 없는 토큰을 쓰면 빌드도 테스트도 통과하고 **화면에서만** 조용히 깨진다.
- 단일 출처는 `src/index.css`의 `:root`. **컴포넌트 CSS에 생 hex나 임의 px을 새로 적지 않는다**
- **시각 언어를 섞지 않는 것**이 "게임이 OS 위에 얹혀 있다"는 인상의 근거다. **사이트와 프로그램(피그마·포토샵·VS코드 등)은 예외**로 자기 팔레트를 자기 CSS 파일 안에 가둔다
- ⚠️ 반투명 표면 위 글자색은 토큰이 아니라 **합성 결과**가 정한다. 눈이나 계산이 아니라 픽셀로 판정한다

## 코딩 컨벤션
1. **게임 수치는 전부 `src/data/`에 있다.** 컴포넌트에 숫자를 적으면 밸런스 테스트가 못 보는 두 번째 출처가 생긴다
2. **`src/systems/`는 순수 함수다.** React import 금지, 상태 mutation 금지, `Math.random` 금지(무작위가 필요하면 **시드를 받는다** — 이 게임은 업무 발생·주말 돌발 이벤트·지원자 생성이 전부 무작위라 이 규칙이 특히 중요하다)
3. **동작하지 않는 컨트롤을 그리지 마라.** 눌러도 아무 일 없는 버튼·갈 데 없는 링크는 만들지 않는다
4. **관계는 한 방향으로만 적는다.** 반대쪽은 파생 함수로 찾는다
5. 창 UI는 반드시 공용 `Window` 컴포넌트를 쓴다
